# BossPilot 产品迭代路线图

> 文档性质：逐期迭代的产品规划与验收基准（参考 RedScope 的 ROADMAP 组织方式）。
> 使用方式：每期开工时，把「本期章节」原文交给 AI，并声明「本期只做该章节范围内的事，
> 范围外一律记入后续期，不提前实现」。每期结束后把该期状态改为「已完成」，
> 并补一份 `docs/phase-N-report.md` 完成报告（参照 `multi-model-phase-1-report.md`）。

## 产品主线

BossPilot 不是「一个能调 AI 的插件」，而是**求职者的长期陪跑副驾**。
每一期迭代必须回答同一个问题：**这期结束后，用户的哪个真实痛点被解决了？**

用户旅程与痛点地图（迭代顺序的依据）：

| 求职阶段 | 真实痛点 | 对应期次 |
|---|---|---|
| 配置工具 | 「选了模型却用不上」 | v0.2 |
| 让 AI 认识我 | 「每次都要重新介绍自己」 | v0.3 |
| 筛选岗位 | 「搜完就丢，无法对比追踪」 | v0.4 |
| 深度分析 | 「AI 不能看着页面帮我判断」 | v0.5 |
| 高频动作 | 「打招呼语/简历诊断每次现问现编」 | v0.6 |
| 长期陪跑 | 「AI 记不住我看过什么、拒过什么」 | v0.7 |
| 信任交付 | 「这个扩展安全吗、质量可靠吗」 | v1.0 |

## v0.1.x：任务流水线与多模型配置基座 — 已完成

已交付能力（现状基线，详见 `multi-model-phase-1-report.md`）：

- 三段式流水线：意图解析 → 确定性采集（zhipin 适配层）→ 批量语义评估与报告；
- 流式对话（OpenAI 兼容协议、SSE、取消、非流式降级）；
- 27 家厂商注册表、四协议模型目录发现、密钥脱敏存储、active model 选择；
- 验证码人机协同、诊断日志下载、旧单模型配置迁移。

主要入口：`lib/pipeline/`、`lib/adapter/`、`lib/llm/`、`lib/providers/`。

## v0.2.0：真实多协议流式生成 — 已完成

**痛点**：用户在设置页精心配好了模型，回到对话页发消息，用的还是旧配置。
「选模型」和「用模型」是断开的，多模型体系目前只是摆设。

**已交付结果**（详见 `multi-model-phase-2-report.md`）：
> 用户选中一个已配置模型后，回到对话页发送消息，BossPilot 使用该模型
> 返回可停止、可报错恢复的流式回复。

已完成：

- Provider generation adapter：`resolveActiveGenerationTarget()` 把 activeModel 指针解析为
  经过目录、密钥、端点与 Host Permission 校验的调用目标；
- OpenAI Completions、OpenAI Responses、Anthropic Messages、Google Generative AI、
  Mistral Conversations 五类生成协议的流式实现，Ollama 走本地 OpenAI-compatible `/v1`；
- 采用 MIT 许可的 `@earendil-works/pi-ai` 公共非 lazy API 与模型元数据；
  通过 MV3 合法的静态 ESM 分块保留精确模型能力，未引入完整 Agent loop；
- 统一内部流式事件和完整消息快照，上层只处理一种状态结构；
- 普通聊天固定使用当前选中模型，失败明确报错，不偷偷切换；
- 停止生成、部分内容保留、会话历史持久化、Port 断线恢复；
- 稳定错误码、密钥跨 delta 防泄露、严格 IPC 上限与可信发送方校验；
- 协议契约、取消、断流、重连、覆盖率和真实 MV3 扩展 E2E。

仍不属于本期：

- 岗位解析/评估的多模型迁移（→ v0.3）；
- 模型自动选择、编排、故障切换（→ 视需求评审）；
- OAuth 登录型 Provider（→ 独立安全里程碑）；
- 工具调用、图片输入与完整 Agent loop。

主要入口：`lib/generation/`、`lib/providers/registry.ts`、`lib/ipc/protocol.ts`、
`entrypoints/background.ts`、`entrypoints/sidepanel/usePort.ts`。

## v0.3.0：求职者档案与上下文个性化 — 规划中

**痛点**：AI 不认识用户。每次对话都要重新交代「我 3 年经验、想要双休、期望 20K」；
岗位评估打分时模型对用户的了解只有一段裸文本简历，打分理由千人一面。

能力点清单：

- 结构化求职档案：简历解析为结构化字段（年限、技能栈、期望薪资、硬性偏好、排除项），
  支持粘贴简历文本一键提取 + 手动修正；
- 档案注入策略：聊天、意图解析、岗位评估三类调用统一注入档案上下文，
  各自有独立的注入模板（聊天要人设感，评估要打分依据）；
- 任务流水线（parseIntent / assessJobs / summarizeReport）迁移到多模型体系，
  与聊天共用 resolveActiveModel，旧 `bosspilot:llm` 配置正式退役；
- 上下文预算与压缩：按模型上下文窗口计算 token 预算，长会话自动压缩旧消息
  （保留系统规则 + 最近对话，旧轮次摘要化），压缩对用户可见可关闭；
- 偏好显式化：用户在对话中表达的持久偏好（「以后都排除外包」）可一键存入档案。

明确不做：跨会话自动记忆（→ v0.7）；多份简历/多求职身份切换（视需求评审）。

主要入口：`lib/profile/`（新）、`lib/llm/prompts.ts`、`lib/agent/context.ts`（新）。

## v0.4.0：岗位工作台与结果沉淀 — 规划中

**痛点**：每次搜索的结果是一次性的——关掉侧边栏就没了。
用户无法回答「上周看过的那个 25K 的岗位叫什么」「这两个 offer 岗位当时评估分各是多少」。
求职是持续数周的对比决策过程，工具却只有「即时问答」。

能力点清单：

- 岗位库：所有采集/评估过的岗位入 Dexie 持久化，按公司+岗位维度去重合并；
- 岗位状态流：待看 → 感兴趣 → 已沟通 → 已投递 → 面试中 → Offer / 淘汰，
  用户手动标记，看板视图（这就是求职者真正的「项目管理」）；
- 跨任务检索与对比：按关键词、城市、薪资、评估分、状态筛选；多选岗位生成对比表；
- 报告产物化：评估报告作为持久记录保存，可重新打开、导出 Markdown/CSV；
- 保留策略：岗位库容量上限与过期清理，一键清空。

明确不做：自动同步 Boss 直聘站内的沟通/投递状态（涉及站内私有数据，需单独安全评审）；
云同步（本地优先，视 v1.x 评审）。

主要入口：`lib/jobs/`（新）、`lib/storage/`、sidepanel 工作台视图（新）。

## v0.5.0：Agent 工具循环与智能化 — 规划中

**痛点**：现在的能力是「固定流水线」——只能跑完整的搜索评估流程。
用户最高频的需求其实是碎片化的：「就看我当前打开的这个 JD，帮我分析」
「对比一下岗位库里这三个」「这家公司在我库里出现过几次」。
系统提示里至今写着「你目前处于纯对话阶段，还不能直接读取网页」。

这一期把 BossPilot 从「流水线执行器」升级为「真正的 loop agent」（Codex 式架构）：

能力点清单：

- 工具注册表：把已有能力工具化——读取当前页面 JD、搜索岗位、读取岗位详情、
  查询岗位库、读取用户档案、生成对比表，每个工具有 Zod 输入 Schema 与硬上限；
- 模型-工具循环：Background 中运行有界的 model-tool loop（轮次上限、可随时停止、
  工具活动实时展示在对话流中）；
- 按需计划与澄清：简单问题直接答；复杂任务先产出可编辑的计划；
  缺关键条件时一次只问最重要的一个问题（不做「每条消息必经的状态机」）；
- 循环级取消与恢复：MV3 Service Worker 重启后能恢复/终止未完成的循环，不留幽灵任务；
- Agent 评测场景：直接回答、澄清、工具调用、越权拒绝、提示注入防护的自动化评测集
  （页面内容永远是不可信输入，不能提升权限或覆盖系统规则）。

明确不做：让模型自由操作页面 DOM（页面动作永远走版本化适配器，模型只能调用有界工具）；
多 agent 协作编排。

主要入口：`lib/agent/`（新：tools.ts / loop.ts / plans.ts / evaluations.ts）。

## v0.6.0：Skills 与提示词模板 — 规划中

**痛点**：求职中的高频动作高度模式化——写打招呼语、诊断简历、准备面试、谈薪，
但每个用户都在对话框里现想现问，问法不好结果就差。产品应当把「最佳问法」沉淀为
一键可用的技能，同时通过模板培养用户的使用习惯与个人风格。

能力点清单：

- 内置求职 Skills（每个 = 输入 Schema + 提示词模板 + 可调用的工具集 + 输出格式）：
  - 打招呼语生成：读取目标 JD + 用户档案，生成 2~3 版风格不同的开场白供选择；
  - 简历诊断：对照目标岗位逐项给出简历修改建议；
  - 面试准备：基于 JD 生成高频问题清单与个性化回答要点；
  - 薪资谈判：结合岗位薪资带与用户期望给谈判策略；
  - Offer 对比：调用岗位库对比表 + 决策建议；
- 模板变量体系：`{档案.技能栈}` `{岗位.JD}` 等变量注入，模板与数据分离；
- 用户自定义：基于内置模板派生个人版本（改语气、改侧重点），本地保存、导入导出；
- 入口设计：对话框上方技能条 + 岗位卡片上的场景化入口（在岗位详情处直接点「打招呼语」）；
- Skill 运行边界：每个 Skill 声明其可用工具白名单，不越权访问。

明确不做：第三方 Skill 市场与签名分发体系（单人使用场景下是过度设计，视 v1.x 评审）；
自动替用户发送任何站内消息（生成 ≠ 发送，发送永远由用户手动完成）。

主要入口：`lib/skills/`（新）、sidepanel 技能条与模板编辑器（新）。

## v0.7.0：求职记忆与长期陪跑 — 规划中

**痛点**：求职持续数周，但 AI 的记忆只有当前会话。用户上周说过「这家公司面过挂了」，
本周推荐里它又出现了；用户的偏好在演化（从「只要双休」到「接受大小周但要 25K+」），
AI 感知不到。

能力点清单：

- 求职记忆库：从对话与操作中沉淀结构化记忆——否决过的公司及原因、面试记录与结论、
  偏好变更历史；写入需用户确认，随时可查看/编辑/删除（记忆透明化）；
- 记忆召回：新任务评估岗位时自动召回相关记忆（「该公司 3 周前被你标记为：面试体验差」），
  召回内容在结果中明确标注来源；
- 定时岗位监控：用户订阅「关键词 + 城市 + 条件」，Chrome alarms 定时增量采集，
  只提醒新出现且评估通过的岗位（有每日预算、串行队列、失败退避；
  遇到登录/验证码进入等待用户状态，不无人值守重试）；
- 求职周报：每周汇总看过/投递/进展与市场观察，生成一份可导出的小结。

明确不做：无人值守自动投递或自动打招呼（永久边界）；云端记忆同步。

主要入口：`lib/memory/`（新）、`lib/automations/`（新）。

## v1.0：工程质量与可信发布 — 规划中

**痛点**：一个常驻浏览器、持有 API Key、能读求职数据的扩展，
用户凭什么信任？开源与工程质量就是信任的来源。

能力点清单（现有 quality/verify 脚本基础上补齐）：

- CI 矩阵（Ubuntu/Windows）、覆盖率门禁全模块化（现在 coverage include 是白名单制）；
- 隐私中心：本地数据总览、全量备份/恢复、一键删除、敏感字段审计；
- 密钥治理：API Key 与业务数据存储分离，备份/诊断/导出永不含密钥；
- 无障碍：键盘导航、焦点管理、屏幕阅读器、对比度检查（Axe）；
- 发布治理：SemVer + Changelog、正式/诊断双构建、Chrome Web Store 上架流程、
  升级迁移与回滚文档；
- 治理文档：CONTRIBUTING、SECURITY、ADR（重大架构决策补记为 ADR，参照 RedScope 格式）。

## 独立里程碑（不排入主线期次）

- **OAuth Provider**（Codex / GitHub Copilot 登录授权）：授权码/设备码 + PKCE +
  token 刷新与撤销，安全模型与 API Key 完全不同，单独立项、单独安全评审；
  v0.2 不包含任何 OAuth UI、权限、令牌或半成品流程；
- **多平台适配**（拉勾/猎聘等）：适配层已按 adapter 模式隔离，是否扩展视产品定位评审。

---

## 永久边界（不是路线图缺口）

以下能力明确永不实现：

- 绕过 Boss 直聘验证码、登录或访问频率限制；
- 无人值守自动投递、自动打招呼、自动回复 HR（所有站内发送动作必须用户手动执行）；
- 读取 Cookie、调用站点未公开接口、账号池；
- 把采集样本描述为平台全量数据；
- 未经授权上传用户简历、岗位数据或对话记录（本地优先，无遥测）；
- 展示或伪造模型隐藏思维链。

## 新需求准入标准

任何计划外的新需求（包括「AI 建议的功能」）先过这七问，再决定排期：

1. 解决哪个真实用户痛点？（说不出场景的不做）
2. 基于真实数据与真实工具结果？（不做演示用的假能力）
3. 副作用是否有界？（轮次/条数/频率有硬上限）
4. 状态是否可持久化恢复？（MV3 随时会杀后台）
5. 失败路径是否明确？（不误报完成）
6. 是否在永久边界之内？
7. 能否自动化测试？

七问全过 → 排入最近的合适期次；过不了 → 记入本文档「独立里程碑」或直接拒绝。
