# BossPilot 产品立项书

> 文档状态：产品主线草案
> 当前项目版本：`0.1.0`
> 目标读者：产品、设计、开发、测试、开源贡献者
> 核心目标：把 BossPilot 从“岗位采集与评估原型”迭代成覆盖岗位发现、判断、材料准备、协助投递、进度管理和面试复盘的 AI 求职执行副驾。

## 1. 一句话定义

BossPilot 是一个运行在 Boss 直聘 PC 网页旁边的 AI 求职副驾。

用户只需要提供自己的简历、求职偏好和一句话目标，BossPilot 负责完成重复的网页浏览、岗位阅读、信息整理、匹配判断和投递准备；用户负责确认个人事实、选择岗位和批准关键操作。

它不是单纯的聊天框，也不是无脑海投机器人。

产品最终要完成这一条闭环：

```text
理解用户
  → 帮用户浏览岗位
  → 判断哪些值得投
  → 准备每个岗位的材料
  → 在用户确认后协助投递
  → 记录回复和面试
  → 根据真实结果改进下一轮求职
```

## 2. 为什么要做

招聘网站已经解决了“哪里有岗位”的问题，但没有解决“用户怎样高质量地完成一次求职”。

今天用户仍然要自己重复：

1. 打开搜索页面；
2. 翻一页又一页的岗位列表；
3. 点开一个岗位；
4. 阅读职位描述和公司要求；
5. 判断是不是外包、驻场、销售包装岗或者信息不完整的岗位；
6. 返回搜索列表；
7. 再打开下一个岗位；
8. 回忆自己的简历是否满足要求；
9. 修改简历和打招呼内容；
10. 投递后再用 Excel、备忘录或记忆记录进度。

真正让用户疲惫的，不只是“看不懂某一个岗位”，而是每天重复几十次“翻页、点击、阅读、返回、比较、复制、粘贴和记录”。

BossPilot 的价值是让 AI 接管这些重复劳动，并把最后的岗位决定和关键操作留给用户。

## 3. 核心用户

第一阶段优先服务：

- 有 1～8 年工作经验、正在跳槽的求职者；
- 每周需要浏览和判断大量岗位；
- 需要根据岗位调整简历和沟通内容；
- 希望提高有效回复率，而不是单纯增加投递数量；
- 互联网、技术、产品、设计和运营岗位求职者。

后续可以扩展：

- 应届生和实习求职；
- 转行用户；
- 多份简历、多求职方向用户；
- 其他招聘网站适配器。

第一阶段不做招聘者筛候选人、企业 ATS 或猎头管理系统。

## 4. 用户的核心痛点

### 4.1 反复翻网页很累

用户需要不断翻搜索结果、点击岗位详情、阅读公司要求、返回列表，再点击下一个。

很多岗位只看标题和薪资无法判断，必须进入详情页查看：

- 真实职责；
- 技术栈或业务要求；
- 经验与学历；
- 公司类型；
- 工作地点；
- 福利与工作时间；
- 是否存在外包、驻场、派遣或频繁出差信号；
- 招聘者是谁；
- JD 没写清楚的地方。

BossPilot 要提供“AI 代浏览执行器”：在用户发起任务后，AI 能够有界、可见地模拟点击岗位、读取详情、验证读取结果、返回原页面并继续查看下一个岗位。

用户不需要亲自读完几十个页面，只需要查看 AI 整理后的候选清单和证据。

### 4.2 招聘网站的筛选条件不够

网站能筛城市、薪资和经验，但无法理解这些要求：

- 排除外包、驻场和人力派遣；
- 希望双休，不接受大小周；
- 希望做 AI 应用，不想继续做传统后台；
- 可以接受经验少一年，但不能接受长期出差；
- 希望团队规模稳定；
- 希望岗位真正使用某项技术，而不是只在 JD 中堆关键词。

BossPilot 要把用户说的人话拆成：

- 硬条件：明确不满足就排除；
- 软条件：结合 JD 和公司信息判断；
- 排除条件：用户不能接受；
- 优先条件：满足时提高推荐顺序；
- 可妥协条件：信息不足时不直接排除。

### 4.3 用户不知道自己是否真的匹配

普通工具经常只给一个“85 分”，却不解释分数从哪里来。

BossPilot 必须拆开说明：

- 技能匹配；
- 经验匹配；
- 行业和项目匹配；
- 城市、薪资与通勤匹配；
- 用户长期偏好匹配；
- 明显风险；
- 信息缺口；
- 简历中缺少的证明。

每项判断都应引用岗位原文或用户材料。没有证据时显示“不确定”，不能让模型猜成事实。

### 4.4 用户的简历和材料没有被真正理解

用户可能上传：

- PDF 简历；
- DOCX 简历；
- 图片或扫描简历；
- 作品集；
- 项目介绍；
- 技能证书；
- 多个方向的简历版本；
- 以前写过的自我介绍和求职信。

如果只是把整个文件直接塞给模型，结果容易遗漏、混淆或超出上下文。

BossPilot 要先把附件解析成“职业事实档案”，再用于岗位匹配和材料生成。

### 4.5 每个岗位都要重复准备材料

同一份简历和同一句招呼语不适合所有岗位。

用户需要针对岗位调整：

- 简历重点；
- 项目顺序；
- 技能关键词；
- 自我介绍；
- 打招呼内容；
- 求职信；
- 面试准备重点。

BossPilot 应自动生成一套岗位专属投递包，但不得编造用户没有提供的经历。

### 4.6 投递后没有管理和反馈

用户容易忘记：

- 哪些岗位看过；
- 哪些岗位投过；
- 使用了哪版简历；
- 给招聘者发了什么；
- 哪些岗位要跟进；
- 哪些岗位进入面试；
- 为什么被拒绝；
- 哪类岗位的回复率更高。

BossPilot 要把岗位、材料、操作、沟通和结果连接成一个本地求职台账。

## 5. 完整用户场景

### 场景 A：上传材料，建立职业事实档案

用户上传简历、作品集或项目介绍。

BossPilot：

1. 识别文件类型；
2. 提取文字、表格和图片中的信息；
3. 对扫描件执行 OCR；
4. 将内容拆成工作经历、项目、技能、教育和求职偏好；
5. 为每条事实保留来源文件和原文位置；
6. 标出冲突、缺失和不确定内容；
7. 让用户确认后才写入长期职业档案。

用户得到的不是“AI 看过文件了”，而是一份可查看、可修改、可追溯的职业事实档案。

### 场景 B：AI 阅读当前岗位

用户打开一个岗位，询问：

> 这个岗位适合我吗？

BossPilot：

1. 读取当前岗位和公司信息；
2. 提取必须条件和加分项；
3. 识别风险与信息缺口；
4. 从职业事实档案中寻找对应证据；
5. 给出分维度判断；
6. 输出“推荐投、可以投、谨慎投、不建议投”；
7. 说明下一步应该补问招聘者什么。

### 场景 C：AI 代用户浏览当前搜索结果

用户说：

> 帮我把这一页的前端岗位看一遍，排除外包和驻场。

BossPilot：

1. 读取当前搜索结果；
2. 记录当前滚动位置和列表上下文；
3. 找到真实岗位卡片；
4. 模拟点击目标岗位；
5. 等待详情页或详情弹层出现；
6. 验证打开的确实是目标岗位；
7. 读取 JD、公司要求和可见招聘者信息；
8. 保存结构化结果和来源；
9. 关闭详情或返回原列表；
10. 确认恢复到原搜索上下文；
11. 继续查看下一个岗位；
12. 达到用户设置的数量、时间或风险上限后停止。

执行过程中用户可以看到：

- AI 正在查看哪个岗位；
- 已查看多少个；
- 哪些被排除；
- 当前停止原因；
- 是否需要登录或处理验证码；
- 是否可以暂停、跳过或取消。

### 场景 D：从一批岗位中做合理决定

BossPilot 将岗位统一成可比较的数据：

- 岗位名称；
- 薪资；
- 城市和区域；
- 公司名称、规模与类型；
- 经验、学历和技能要求；
- 工作内容；
- 风险信号；
- 用户匹配证据；
- 信息缺口；
- 来源 URL 和读取时间。

然后结合用户简历和求职偏好输出：

- 最值得投的岗位；
- 可以作为备选的岗位；
- 需要先问清楚再投的岗位；
- 不建议投的岗位；
- 每个结论的理由；
- 推荐投递顺序。

### 场景 E：生成岗位专属投递包

用户选择岗位后，BossPilot 生成：

- 简历修改建议；
- 简历经历排序；
- 建议强调的项目；
- 需要补充但必须由用户确认的内容；
- 个性化打招呼文案；
- 自我介绍；
- 求职信；
- 投递前问题清单；
- 面试准备清单。

所有修改通过差异对比展示。用户可以逐条接受、拒绝或编辑，原始简历不会被覆盖。

### 场景 F：协助完成投递

BossPilot 将投递分为三级：

1. **内容辅助**：生成内容，由用户复制；
2. **操作辅助**：预填页面，用户预览后点击发送或投递；
3. **授权自动化**：在平台许可或正式接口支持下，按用户确认过的队列执行。

公开版本默认做到第二级。

一次协助投递包括：

1. 选择岗位；
2. 选择简历版本；
3. 生成或选择招呼文案；
4. 展示即将填写和发送的内容；
5. 用户明确确认；
6. 预填页面；
7. 用户完成最终发送；
8. 保存岗位、材料版本、时间和结果；
9. 失败时保留现场并给出恢复操作。

### 场景 G：投递后的沟通和跟进

用户可以询问：

> 我最近投了哪些岗位？

> 今天应该跟进谁？

> 这个招聘者刚才问了什么，我应该怎么回答？

BossPilot：

- 管理岗位状态；
- 总结当前可见沟通内容；
- 生成多个回复版本；
- 提醒需要确认的薪资、地点、工作时间和面试安排；
- 生成礼貌跟进文案；
- 保存用户确认后的沟通摘要。

### 场景 H：面试副驾

收到面试后，BossPilot 结合岗位、公司和用户真实经历生成：

- 岗位与公司速览；
- 可能的面试题；
- 针对简历项目的追问；
- STAR 回答框架；
- 需要复习的技术点；
- 反问面试官的问题；
- 模拟面试；
- 面试后的复盘模板。

### 场景 I：根据真实结果改进下一轮求职

BossPilot 根据用户主动记录的回复、面试和录用结果分析：

- 哪类岗位回复率高；
- 哪版简历效果好；
- 哪种打招呼方式更有效；
- 哪些技能是真正短板；
- 哪类公司不适合用户；
- 下一阶段应该主攻什么方向。

学习结果必须可以解释、修改、关闭和清除。

## 6. 产品能力地图

| 模块 | 解决的问题 | 主要能力 |
| --- | --- | --- |
| 职业事实档案 | AI 不真正了解用户 | 附件解析、OCR、结构化、事实确认、版本管理 |
| AI 代浏览执行器 | 用户反复翻页点击很累 | 卡片定位、模拟点击、详情验证、读取、返回、暂停恢复 |
| 岗位理解器 | JD 又长又模糊 | 职责、要求、公司、风险、缺口结构化 |
| 岗位决策引擎 | 用户不知道值不值得投 | 硬条件、软条件、证据匹配、分层推荐 |
| 投递材料工作台 | 每个岗位都要重复改材料 | 简历差异、招呼语、自我介绍、求职信 |
| 投递执行器 | 复制粘贴和记录很重复 | 队列、预填、预览、确认、失败恢复 |
| 求职台账 | 投递后失去管理 | 去重、状态、材料版本、时间线、提醒 |
| 沟通与面试副驾 | 投递和面试割裂 | 对话摘要、回复草稿、面试准备、复盘 |
| 个性化学习 | 用户没有从结果中学习 | 回复率、版本对比、方向建议、技能差距 |
| 隐私与安全中心 | 简历和沟通内容敏感 | 本地存储、外发预览、权限、删除、备份 |

## 7. AI 在产品中怎样落地

BossPilot 不以“用了多少 AI 名词”为目标。每一种 AI 能力都必须对应一个真实用户问题。

### 7.1 多模态文档理解

大白话：让 AI 不只能读输入框，还能读 PDF、Word、图片简历和作品集。

用于：

- 简历解析；
- 扫描件 OCR；
- 项目材料提取；
- 多文件信息合并；
- 冲突信息提示。

### 7.2 长期记忆

大白话：用户不用每次重新介绍自己。

长期记忆只保存用户确认过的内容，包括：

- 真实经历；
- 技能证据；
- 求职偏好；
- 不接受条件；
- 简历版本；
- 历史岗位和投递结果。

### 7.3 RAG 与证据召回

大白话：需要判断一个岗位时，AI 从原始简历和项目材料中找相关证据，而不是凭印象回答。

例如岗位要求“复杂前端性能优化”，AI 应找到用户项目中对应的性能优化经历；找不到就明确说简历缺少证据。

### 7.4 Agent 与工具调用

大白话：AI 不只是回答，而是能把目标拆成步骤并使用浏览器工具完成。

典型步骤：

```text
理解目标
  → 制定有界计划
  → 找到岗位卡片
  → 点击并读取
  → 验证是否成功
  → 保存结果
  → 返回并继续
```

### 7.5 确定性站点适配器

大白话：真正点击和读取网页时，不让模型每次猜按钮在哪里。

模型负责决定“看哪个岗位、为什么看”；版本化适配器负责“具体点哪里、怎样确认打开成功、怎样返回”。

### 7.6 结构化输出

大白话：AI 不能只输出一段看起来不错的话，而要给程序可检查的数据。

例如匹配结果必须包含：

- 结论；
- 分维度得分；
- 支持证据；
- 风险；
- 信息缺口；
- 建议动作。

### 7.7 检查器与真实性守卫

大白话：AI 做完以后，再有一个检查步骤负责找错。

检查：

- 是否编造经历；
- 是否误读岗位；
- 是否把猜测写成事实；
- 是否遗漏硬条件；
- 是否准备执行未确认的操作；
- 是否把一个岗位的信息混入另一个岗位。

### 7.8 Human-in-the-loop

大白话：重复劳动交给 AI，关键决定留给用户。

以下动作必须有人确认：

- 写入长期职业档案；
- 采用 AI 修改后的简历；
- 发送打招呼内容；
- 提交简历；
- 自动跟进；
- 开启更高等级的页面自动化。

### 7.9 反馈学习

大白话：BossPilot 根据真实回复和面试结果越来越了解用户，而不是永远使用固定提示词。

反馈只影响可解释的偏好和权重，用户可以查看和重置。

## 8. 产品主流程

```text
首次使用
  → 配置模型
  → 上传简历/附件
  → AI 解析
  → 用户确认职业事实档案

开始找工作
  → 用户描述目标
  → AI 解析硬条件和软条件
  → 用户确认任务范围
  → AI 浏览当前页面岗位
  → 逐个读取并验证详情
  → 结合职业档案评估
  → 输出候选清单和证据

准备投递
  → 用户选择岗位
  → AI 生成岗位专属材料
  → 真实性检查
  → 用户编辑和确认
  → 页面预填
  → 用户完成最终发送

投递之后
  → 保存投递状态
  → 跟进和沟通辅助
  → 面试准备
  → 记录结果
  → 改进下一轮推荐
```

## 9. 迭代路线

### v0.1：三段式技术原型——当前已有

当前实现：

- 自然语言求职需求解析；
- Boss 直聘搜索和详情适配；
- 岗位结构化提取；
- 软条件过滤；
- 匹配评分；
- 结构化岗位结果；
- 验证码人工处理；
- 任务取消。

当前版本证明了“确定性页面适配器 + AI 语义判断”的技术路线，但还没有形成完整求职产品闭环。

### v0.2：职业事实档案与单岗位决策

用户可以说：

> 读一下我的简历，再告诉我这个岗位适不适合。

必须实现：

- PDF、DOCX、文本和图片附件导入；
- 文本提取和 OCR；
- 职业事实结构化；
- 来源和原文引用；
- 用户确认与纠错；
- 多个简历版本；
- 当前岗位读取；
- 分维度匹配；
- 风险和信息缺口；
- 保存岗位。

本版引入的 AI 能力：

- 多模态文档理解；
- 结构化输出；
- 职业长期记忆；
- 证据召回；
- 真实性检查。

完成标准：

- AI 不会把未确认内容写入职业档案；
- 每条岗位判断能指向 JD 或用户材料证据；
- 没有证据时显示“不确定”；
- 原始附件和解析结果可以删除；
- 至少覆盖一组真实 PDF、DOCX、图片和扫描件测试样本。

本版不做：

- 自动投递；
- 自动发送消息；
- 无人值守批量浏览。

### v0.3：AI 代浏览与岗位候选清单

用户可以说：

> 别让我一个个点了，帮我把当前这些岗位看一遍。

必须实现：

- 当前搜索页岗位发现；
- 真实卡片重新定位；
- 模拟点击；
- 详情页或弹层出现验证；
- 目标岗位身份验证；
- JD、公司和招聘者可见信息读取；
- 关闭详情或返回列表；
- 原滚动位置和搜索上下文恢复；
- 岗位去重；
- 跳过、暂停、恢复和取消；
- 登录、验证码、访问限制人工接管；
- 数量、时间、错误和重试硬上限；
- 执行进度和停止原因；
- 本地任务检查点；
- 站点改版诊断。

本版引入的 AI 能力：

- Agent 计划；
- 浏览器工具调用；
- 结果验证；
- 确定性适配器；
- 任务检查点与恢复。

完成标准：

- 用户始终知道 AI 正在查看哪个岗位；
- 每次点击后验证确实打开了目标岗位；
- 返回后能继续原列表，而不是从头开始；
- 同一岗位不会重复读取；
- 浏览器后台被回收后能从检查点恢复；
- 连续失败会停止，不会无限点击或刷新；
- 验证码由用户处理，不尝试绕过。

本版不做：

- 不可见的后台无限采集；
- 自动跨页长时间运行；
- 绕过网站限制。

### v0.4：岗位决策与推荐排序

用户可以说：

- 硬条件、软条件、排除条件和优先条件；
- 用户可编辑的条件确认卡；
- 多岗位统一字段；
- 分维度匹配；
- 外包、驻场、派遣、工作时间和出差信号识别；
- 推荐投、可以投、先询问、不建议投四级结论；
- 多岗位对比；
- 推荐投递顺序；
- 每个结论的证据和不确定性。

本版引入的 AI 能力：

- 约束推理；
- 多来源证据合并；
- 可解释评分；
- 检查器二次审查。

完成标准：

- 用户可以修改 AI 解析出的所有求职条件；
- 不用单一总分掩盖硬条件不满足；
- 推荐理由和排除理由都有证据；
- 信息不足时给出需要询问招聘者的问题；
- 输出可以直接进入投递准备队列。

- 真实性守卫；
- 用户逐条接受、拒绝和编辑；

本版引入的 AI 能力：

- 基于事实档案的内容生成；
- 差异编辑；
- 幻觉和事实冲突检查。

完成标准：

## 10. 核心数据对象

产品需要围绕以下对象设计，而不是只保存聊天消息：

| 对象 | 作用 |
| --- | --- |
| `CareerProfile` | 用户确认过的职业事实、技能和偏好 |
| `SourceAttachment` | 简历、作品集、证书和解析状态 |
| `ResumeVersion` | 原始简历和岗位专属版本 |
| `SearchIntent` | 用户本次求职的硬条件、软条件和优先级 |
| `JobPosting` | 规范化岗位、公司、招聘者和来源 |
| `JobEvidence` | JD 原文、附件原文和判断引用 |
| `JobAssessment` | 分维度匹配、风险、缺口和建议 |
| `BrowseRun` | AI 浏览任务、进度、检查点和停止原因 |
| `ApplicationPack` | 简历、招呼语、自我介绍和问题清单 |
| `Application` | 投递状态、材料版本、时间和操作记录 |
| `ConversationSummary` | 用户确认保存的沟通摘要 |
| `InterviewRun` | 面试准备、模拟和复盘 |
| `OutcomeFeedback` | 回复、面试、拒绝和录用结果 |

## 11. 产品安全边界

BossPilot 明确不做：

- 绕过登录、验证码或访问限制；
- 破解平台私有接口；
- 读取 Cookie 或账号密码；
- 账号池；
- 无限翻页和无人值守采集；
- 用户不知情的自动投递；
- 用户不知情的自动发消息；
- 编造简历经历；
- 把模型推断写成网页事实；
- 上传未向用户说明的数据；
- 用投递数量制造虚假成功。

页面浏览和操作遵循：

- 用户主动发起；
- 范围清楚；
- 过程可见；
- 数量有界；
- 可以暂停；
- 每步验证；
- 失败诚实；
- 关键副作用人工确认。

## 12. 隐私原则

- 默认本地保存；
- 项目方不建设保存用户简历的默认云端；
- API Key 与业务数据分开保存；
- 用户可以选择只在当前浏览器会话保存密钥；
- 发送给模型前展示数据范围和目标服务商；
- 不向模型发送与当前任务无关的附件内容；
- 原始附件、解析结果、岗位和投递记录可以单独删除；
- 备份和诊断文件排除 API Key、Cookie 和认证信息；
- 不做默认遥测。

## 13. 产品指标

北极星指标：

> 每周完成的高质量、个性化、用户确认投递数。

核心结果指标：

- 有效回复率；
- 面试邀请率；
- 从打开岗位到做出决定的时间；
- 从选择岗位到完成投递的时间；
- AI 推荐岗位的实际投递率；
- 岗位专属材料的实际使用率；
- 用户对 AI 判断的接受和修改比例；
- 重复投递率；
- 页面读取和详情验证成功率；
- 任务暂停后的恢复成功率；
- 单次有效投递的模型成本。

不作为核心成功指标：

- 单纯采集了多少岗位；
- 单纯调用了多少次模型；
- 单纯自动点击了多少次；
- 单纯投递了多少份简历。

## 14. MVP 范围

如果第一阶段只有 6～8 周，应优先完成：

1. 附件解析和职业事实档案；
2. 当前岗位读取；
3. 当前页面有界代浏览；
4. 证据化岗位匹配；
5. 候选岗位清单；
6. 岗位专属投递材料。

也就是完成 v0.2～v0.5 的最小闭环。

这一阶段暂不追求全自动投递。只要 BossPilot 能稳定做到：

> 用户上传简历后，不再亲自读完几十个岗位，AI 能帮他看、帮他比较、告诉他为什么值得投，并准备好真实可用的材料。

产品就已经产生了明确价值。

## 15. 与现有代码的关系

现有代码不是推倒重来，而是作为基础继续演进：

- 保留三段式“意图解析 → 确定性网页操作 → AI 语义评估”；
- 保留 Boss 直聘站点适配器；
- 保留任务取消和验证码人工处理；
- 将内存任务升级为持久化任务；
- 将自由文本简历升级为附件与职业事实档案；
- 将单一匹配分升级为证据化决策；
- 将结构化结果升级为岗位、材料和投递台账；
- 将批量采集原型收敛为用户发起、过程可见、数量有界的 AI 代浏览；
- 在平台许可之前，将自动投递收敛为预填、预览和人工确认。

BossPilot 的长期产品主线是：

> AI 先理解用户，再替用户完成繁琐的网页浏览，最后给出可信的岗位决定，并继续完成材料准备、投递协助、进度管理和面试复盘。
